## Введение

Магазину настольных игр нужно поддерживать актуальные сведения об ассортименте, остатках, заказах и поставщиках. При оформлении заказа покупателю важны фильтры по характеристикам игры и доступное количество. Сотруднику нужен доступ к складским данным и заказам, а администратору — к учётным записям.

Цель проекта — разработать настольную информационную систему для магазина с хранением данных в PostgreSQL и разграничением операций по ролям. Задачи проекта включают проектирование базы, разработку интерфейса, регистрацию и вход, обработку каталога и заказов, формирование PDF-чека и проверку рабочих сценариев.

## 1 Анализ предметной области

Покупатель выбирает товар, добавляет его в корзину и оформляет самовывоз. Сотрудник ведёт остатки, принимает заказ, обрабатывает его и фиксирует выдачу. Поставщик может быть связан с несколькими играми, одна игра — с несколькими поставщиками. Администратор выполняет задачи сотрудника и управляет доступом пользователей.

| Аналог | Достоинства по ТЗ | Ограничения по ТЗ |
|---|---|---|
| Hobby Games | Ассортимент, поиск, фильтры по характеристикам, подробные карточки и заказ | Много разделов, ориентация на интернет-магазин |
| GaGa.ru | Категории, поиск, большой каталог, подборки и описания | Браузерная работа, насыщенные страницы, в обзоре отсутствуют функции внутреннего управления |
| Мосигра | Каталог, категории, поиск и навигация | Ориентация на интернет-продажи, в обзоре отсутствует нужное разделение функций по ролям |

Для курсового проекта достаточно каталога с фильтрами и рабочего пространства сотрудников одного магазина. Заказ оформляется для получения в магазине, дальнейшее движение отражают статусы.

## 2 Проектирование

### 2.1 Архитектура и распределение прав

Интерфейс PyQt6 передаёт данные форм в сервисы. Сервисы проверяют значения и роль, репозитории исполняют параметризованные запросы PostgreSQL и управляют транзакциями. Матрица в [документе трассируемости](traceability.md#матрица-прав) показывает действия каждой роли. Навигация строится по той же матрице, которую используют проверки в сервисах. Диаграммы взаимодействия и сценариев приведены в [приложении с алгоритмами](design/processes.md).

### 2.2 База данных

Таблицы пользователей, игр, категорий, заказов и поставщиков содержат данные своих сущностей. Избранное, корзина, позиции заказа и ассортимент поставщика хранятся отдельными отношениями. Внешние ключи защищают связанные записи. Уникальный индекс по почте в нижнем регистре предотвращает дубликаты. [ER-диаграмма и словарь данных](design/database.md) описывают поля, связи и нормализацию.

### 2.3 Математическое обеспечение

Пусть Ci — цена единицы товара i, Ki — заказанное количество, Oi — доступный остаток. Стоимость позиции Pi = Ci × Ki. Итог S = ΣPi. Количество единиц N = ΣKi. Заказ допустим при Ki ≤ Oi по каждой позиции. После оформления новый остаток Oi′ = Oi − Ki. При изменении состава нового заказа доступный остаток учитывает также ранее списанное количество этого заказа.

Деньги хранятся в `numeric(10,2)`, в Python расчёты выполняются с `Decimal`. Цена копируется в строку заказа, поэтому последующее изменение цены в каталоге не меняет сохранённый заказ.

### 2.4 Интерфейс и PDF

Окна входа и регистрации используют тёмную тему. После входа слева видны разделы текущей роли, справа открывается выбранный раздел. Профиль позволяет хранить локальную настройку темы. При подготовке PDF сервис запрашивает данные заказа, клиента и позиций, проверяет доступ и пересчитывает суммы. Чек содержит заголовок магазина, номер, дату, покупателя, таблицу позиций, общее количество и итог.

### 2.5 Надёжность и защита данных

Валидация выполняется перед записью. Ограничения БД дополнительно обеспечивают корректность ролей, статусов и числовых значений. Неудачное оформление откатывает изменения, ошибки ввода и подключения показываются в диалоге. Пароли хешируются с помощью bcrypt. Регистрация требует согласия на обработку персональных данных. Конфигурация самостоятельного развёртывания принимает подключения к PostgreSQL только на петлевом адресе. Требование размещать локальную базу на территории РФ относится к эксплуатации системы.

## 3 Реализация

Разработка выполняется на Python. PyQt6 отвечает за настольный интерфейс, PostgreSQL — за сохранность и согласованность записей, psycopg2 — за передачу запросов, ReportLab — за формирование PDF. Git ведёт историю проекта. Проект можно открыть в PyCharm.

- `main.py`, `ui/windows/`, `ui/widgets/` — запуск, навигация, каталог, рабочие разделы и формы.
- `services/auth.py`, `services/permissions.py` — регистрация, вход и разграничение доступа.
- `services/inventory.py`, `services/order_flow.py` — проверка данных и операции с магазином.
- `repositories/`, `db/` — запросы, соединение, создание и заполнение структуры.
- `services/calculations.py`, `services/receipts.py`, `services/receipt_pdf.py` — вычисления, права на чек и запись файла.

Функция `register` сравнивает пароли и проверяет согласие. Пароль передаётся в `bcrypt.hashpw` с солью `bcrypt.gensalt()`. Репозиторий получает строку хеша. При входе `bcrypt.checkpw` проверяет введённый пароль. После проверки в интерфейс передаются данные профиля без хеша.

При оформлении заказа репозиторий блокирует товары в порядке идентификаторов:

```sql
SELECT id, name, price, quantity FROM products
WHERE id = ANY(%s) ORDER BY id FOR UPDATE
```

В той же транзакции сохраняются позиции и итог, а корзина очищается. Если остатка недостаточно, исключение приводит к откату. Такой порядок позволяет двум клиентам конкурировать за последний экземпляр без отрицательного остатка.

Для клиента сервис чека передаёт идентификатор владельца в запрос заказа. Для сотрудника доступ определяется ролью. PDF пишется во временный файл в выбранной папке и затем заменяет целевой файл после успешного формирования.

## 4 Испытания

[Программа и методика испытаний](test_program.md) задаёт исходные данные, действия и ожидаемые результаты. Автоматический набор проверяет валидацию и изоляцию тестовой базы, повторное создание схемы и загрузку демонстрационного набора проверяют на отдельной базе. Сквозной сценарий охватывает применение прав, оформление и получение заказа, а также работу с чеком. В контрольном прогоне прошли 74 автоматические проверки. Отдельный сквозной сценарий на PostgreSQL проверил окна трёх ролей, конкурентное оформление заказа, пересчёт и возврат остатков, статусы, поставщиков, доступ к заказам и формирование PDF с кириллицей. Для проверки PDF использован доступный кириллический шрифт в тестовой среде. Фактический протокол приёмки заполняется по результатам выполнения ПМИ.

## Заключение

В проекте реализованы роли покупателя, работника и администратора, операции с каталогом, корзиной, заказами, поставщиками и профилями. Хранение заказов и изменение остатков связаны транзакцией. Дальнейшее развитие может включать дополнительные средства работы с каталогом и уточнение модели ролей.
